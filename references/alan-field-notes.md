# Alan 的 Builder 实战摘录

这些材料用于解释“为什么形成某条方法”，不是要求小白照搬完整工程体系。

## 1. CC Quick Installer：把入学失败面产品化

**场景**：纯小白连 Node.js、PATH、Claude Code 和配置文件都不理解，国内网络又可能无法稳定访问 GitHub。

**做法**：安装器把环境检查、Node.js、Claude Code、PATH 和模型配置放进一个界面；默认使用国内镜像，同时保留直连、手动下载、旧终端重开和老 Mac 的兜底说明。

**形成的判断**：对小白而言，“写清安装文档”并没有消除安装摩擦。能够检测、重试、解释失败并验证真实调用，才叫完成入学。

**课程化动作**：学生不背 PATH；让 Agent 检查环境、执行最小动作，并用版本命令、真实模型回复和临时文件读写三层验证。

## 2. Project Template：把规范写成机器信号

**场景**：长时间让 Agent 开发时，单靠提示“写好代码、注意测试”无法稳定约束结果。

**做法**：用 Git 作为交接总线，把 PRD、Spec、项目规则、测试、CI 和一条 `verify` 命令固化进模板。PRD 记录人的意图，Spec 记录 Agent 的技术承诺，冲突时必须升级给人裁决。

**形成的判断**：好的流程不追求 Agent 第一次全对，而是让错误更早暴露、纠错更便宜。文档模板本质上是在给 Agent 的注意力编程。

**课程化动作**：小白先写一页项目卡和三个验收样例；只有项目进入长期维护后，才逐步引入双稿 PRD、Spec、CI 和多层 Review。

## 3. Glint：设计探索推翻 PRD v0

**场景**：Glint 在 v0.5 阶段推翻过核心交互。它说明早期 PRD 不可能准确预言最终产品，视觉与交互探索本身就是需求发现。

**做法**：先写一页 PRD v0，保留问题、用户、核心流程和非目标；设计方向拍板后再把真实决策反写为 PRD v1，之后才生成更具体的技术 Spec 和施工计划。

**形成的判断**：迭代不是失败。真正危险的是把未经探索的 v0 当成不可修改的规格，或者让原型、PRD 和实现各自成为不同版本的“真相”。

**课程化动作**：小白先写薄项目卡；做出可见原型后必须回头修订，而不是因为改需求感到“前面白做了”。

## 4. 设计：先发散方向，再在代码里收敛

**场景**：视觉工具适合讨论信息架构和核心交互，却不适合为按钮间距反复走漫长回合。

**做法**：先讨论 PRD 与 Design System，再用 Lovable 或 baoyu-design 快速生成一版可见原型；Figma、Pencil 通过 MCP 让 Agent 操作，学生负责反馈和拍板。方向确定后回到真实项目，用热重载收敛细节。

**形成的判断**：原型是需求发现和视觉规格，不自动等于最终工程代码。工具负责扩大选择，人负责判断什么是对的。

## 5. 测试铁律：Agent 的肯定句不是证据

**场景**：Agent 可能误读代码、遗漏边界、把配置存在当成链路可用，甚至没有真正运行命令就说“完成”。

**做法**：关键行为尽量写成测试并实际运行；UI 必须真实操作；跨模型 Review 不能用同一 Agent 的自查冒充。无法运行就明确标记未验证。

**形成的判断**：完成不是一句自然语言，而是一组可重放的机器和行为证据。
