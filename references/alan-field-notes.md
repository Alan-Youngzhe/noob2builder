# Alan 的 Builder 实战摘录

这些材料用于解释“为什么形成某条方法”，不是要求小白照搬完整工程体系。

## Alan 当前默认的 0→1 顺序

```text
brainstorming 发散探索
→ GrillMe 需求访谈与收敛
→ PRD v0
→ Design System
→ Lovable 原型
→ 根据原型反写 PRD v1
→ AI 产出 Spec
→ 敏捷开发 MVP
→ 验证核心可行性
→ 再补工程质量、测试和跨模型 Review
→ 正式发布与反馈
```

这条顺序体现了三个判断：

1. 先把用户意图聊清，但不假装 PRD v0 已经是最终答案；
2. 先给原型设计约束，再通过可见原型继续发现需求；
3. 产品可行性尚未验证时先敏捷做 MVP，确认值得继续后再投入完整工程体系和交叉 Review。

## PRD 的评判标准：能否让实现收敛

即使单人开发，也要把自己的 AI 当成团队里的开发者。好的 PRD 不是字数多，而是把同一份 PRD v1、Design System 和原型交给不同开发者或不同 AI，他们不依赖作者继续口头补充，也能理解相同的用户、核心流程、范围、交互意图和完成标准，最后做出的核心产品行为大差不差。

这里不要求代码结构和技术实现完全一致；技术承诺由 Spec 进一步收敛。PRD 负责产品意图，Design System 和原型负责可见交互，Spec 负责技术方案，三者一起形成团队可执行的合同。

因此需要先看见原型再反写 PRD：很多信息架构、页面状态和交互判断在纯文字阶段还是隐性的，Lovable 等工具先把它们变成可以指认、删除和修改的对象，PRD v1 再把已拍板的内容写回权威文档。

课程中的验收动作叫“独立交接测试”：让一个没有参加需求讨论的 Agent 只读 PRD v1、Design System 和原型，复述用户流程、非目标、关键状态和验收标准，并给出实施计划。仍需猜核心决策，就继续修改 PRD，而不是怪开发者理解能力差。

## 1. CC Quick Installer：把入学失败面产品化

**场景**：纯小白连 Node.js、PATH、Claude Code 和配置文件都不理解，国内网络又可能无法稳定访问 GitHub。

**做法**：安装器把环境检查、Node.js、Claude Code、PATH 和模型配置放进一个界面；默认使用国内镜像，同时保留直连、手动下载、旧终端重开和老 Mac 的兜底说明。

**形成的判断**：对小白而言，“写清安装文档”并没有消除安装摩擦。能够检测、重试、解释失败并验证真实调用，才叫完成入学。

**课程化动作**：学生不背 PATH；让 Agent 检查环境、执行最小动作，并用版本命令、真实模型回复和临时文件读写三层验证。

## 2. Project Template：把规范写成机器信号

**场景**：长时间让 Agent 开发时，单靠提示“写好代码、注意测试”无法稳定约束结果。

**做法**：用 Git 作为交接总线，把 PRD、Spec、项目规则、测试、CI 和一条 `verify` 命令固化进模板。PRD 记录人的意图，Spec 记录 Agent 的技术承诺，冲突时必须升级给人裁决。

**形成的判断**：好的流程不追求 Agent 第一次全对，而是让错误更早暴露、纠错更便宜。文档模板本质上是在给 Agent 的注意力编程。

**课程化动作**：小白先用 brainstorming 发散问题、用户和方向，再用 GrillMe 逐题收敛，形成薄 PRD v0；原型后反写 PRD v1，并让 AI 生成一份轻量 Spec。只有 MVP 通过可行性门、项目准备长期维护后，才逐步引入完整测试矩阵、CI 和多层 Review。

## 3. Glint：设计探索推翻 PRD v0

**场景**：Glint 在 v0.5 阶段推翻过核心交互。它说明早期 PRD 不可能准确预言最终产品，视觉与交互探索本身就是需求发现。

**做法**：先写一页 PRD v0，保留问题、用户、核心流程和非目标；设计方向拍板后再把真实决策反写为 PRD v1，之后才生成更具体的技术 Spec 和施工计划。

**形成的判断**：迭代不是失败。真正危险的是把未经探索的 v0 当成不可修改的规格，或者让原型、PRD 和实现各自成为不同版本的“真相”。

**课程化动作**：小白先写薄项目卡；做出可见原型后必须回头修订，并用独立 Agent 做交接测试，而不是因为改需求感到“前面白做了”。

## 4. 设计：先发散方向，再在代码里收敛

**场景**：视觉工具适合讨论信息架构和核心交互，却不适合为按钮间距反复走漫长回合。

**做法**：先用 brainstorming 发散，再用 GrillMe 形成 PRD v0，构思轻量 Design System，把它们交给 Lovable 生成可见原型；Figma、Pencil 可通过 MCP 让 Agent 操作。学生查看原型后反写 PRD v1，再让 AI 生成 Spec。方向确定后回到真实项目，用热重载收敛细节。

**形成的判断**：原型是需求发现和视觉规格，不自动等于最终工程代码。工具负责扩大选择，人负责判断什么是对的。

## 5. 测试铁律：Agent 的肯定句不是证据

**场景**：Agent 可能误读代码、遗漏边界、把配置存在当成链路可用，甚至没有真正运行命令就说“完成”。

**做法**：MVP 阶段保留最低安全与核心行为 smoke 验收；可行性通过后，关键行为尽量写成测试并实际运行，UI 必须真实操作，跨模型 Review 不能用同一 Agent 的自查冒充。无法运行就明确标记未验证。

**形成的判断**：完成不是一句自然语言，而是一组可重放的机器和行为证据。
