# 什么叫"好代码"：五个可检查的标准

## 目标

学生能用五条具体标准评价一段代码，而不是凭"看着乱"下判断；并且知道哪一条对自己的项目最要紧。

## 讲授

"代码质量"听起来很虚，拆成五条就都能检查了。注意顺序——**它们不是并列的，是有优先级的**：

**一、正确**——它做的是不是需求要的那件事。这条排第一，其它四条都建立在它之上。漂亮但做错事的代码价值为零。

**二、简单**——能不能在不看别处的情况下看懂这一段。检查方法很土：随便挑一个函数，问自己"要理解它，我得同时记住多少东西？"超过五六个就是太复杂了。Agent 特别容易写出"功能都对但绕了三层"的代码。

**三、可测试**——能不能在不启动整个系统的情况下验证它。一个函数如果直接在内部读环境变量、连数据库、发网络请求，它就很难测。可测试性差通常不是测试的问题，是**这段代码把决策和副作用混在一起了**。

**四、可修改**——改一个需求要动几个地方。同一个业务概念散落在五处，每次都得五处一起改还容易漏——这才是真正的技术债，比"命名不好看"严重得多。

**五、可运维**——出问题时看得见吗。有没有日志、报错信息说不说得清、能不能定位到具体请求。凌晨两点线上炸了，这条决定你是十分钟还是三小时。

**给小白最实用的一条判断**：这五条里，**你的项目最缺哪一条？**先补那一条。全都想补，通常一条都补不成。

对 Agent 尤其要说清楚：**它默认倾向于"能跑"，也就是只优化第一条。**你不提，它不会主动考虑可测试和可运维。所以提需求时要明确：这段代码后面要被测试，副作用请分离出来。

常见误区：把"整洁"当成第一目标（正确性优先）；为了可测试而过度抽象（三层接口包一个函数）；追求覆盖率而不是关键路径。

## 实验

1. 从项目里挑一个你最不敢碰的文件；
2. 用五条标准逐条打分，每条写一句具体理由，不许写"还行"；
3. 让 Agent 独立打一遍分，对比结论，不一致的地方追问依据；
4. 挑出得分最低的那一条，让 Agent 提出**最小改动**方案——不是重写，是改最少的地方让这一条变好；
5. 实施，然后确认行为没变（有测试就跑测试，没有就手动走一遍核心路径）；
6. 用 `git diff --stat` 看改了多少行，超过 200 行就说明"最小改动"没做到，退回去重来。

## 常见误区

- 五条同时补等于一条都没补；
- 重写比改造更容易失控，尤其在没有测试保护的时候；
- 行为没变要有证据，不能只凭"我觉得没影响"。

## 证据

一份五条打分表，含具体理由；第 4 步的最小改动方案和真实 diff；`git diff --stat` 输出；行为未变的验证记录。
