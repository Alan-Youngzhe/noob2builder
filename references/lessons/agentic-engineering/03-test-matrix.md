# 从行为清单生成测试矩阵

## 目标

学生能把体检得到的行为清单和风险清单，变成一张"什么行为、用哪层证据、成本多少"的表，并知道哪些地方**故意不测**。

## 讲授

旧项目补测试最容易犯的错是"从头开始补"——从第一个文件往下写单元测试，写了两周覆盖率上去了，线上该炸还炸。因为**覆盖率保护的是代码，不是行为**。

正确的入口是上一节的两张清单：**行为清单说要保护什么，风险清单说先保护哪个。**

矩阵长这样：

| 行为 | 风险等级 | 最便宜的证据 | 成本 | 现状 |
|---|---|---|---|---|
| 用户提交表单后收到确认邮件 | 高（外部副作用） | 集成测试 + 邮件服务打桩 | 中 | 缺 |
| 金额计算含税四舍五入 | 高（钱） | 单元测试 | 低 | 缺 |
| 管理员才能删除记录 | 高（权限） | 集成测试，带越权用例 | 中 | 缺 |
| 首页列表按时间倒序 | 低（显示） | 手动看一眼 | 极低 | 不测 |

**"最便宜的证据"是核心列。**原则是：**能在低层证明的，绝不上高层。**纯计算逻辑用单元测试，跨模块用集成测试，真实用户旅程才用 E2E——E2E 又慢又脆，一个项目有三五个关键的就够了。层级的完整定义见 `../../courses/testing-verification.md`，需要系统学就转过去，这里只做矩阵。

**"不测"是合法选项，而且必须显式写出来。**上表最后一行就是。写"不测"和漏掉它完全不同：前者是判断，后者是事故。每条"不测"要有理由，通常是"坏了不疼且一眼能看见"。

**排序规则**：风险高、成本低的先做。风险高但成本也高的（比如支付全流程 E2E），先用更便宜的层挡一部分，别一开始就啃硬骨头。

常见误区：按文件顺序补测试；追求覆盖率数字；给显示类行为写 E2E；不写"不测"清单，导致后面的人以为漏了。

## 实验

1. 拿出体检的行为清单和风险清单；
2. 逐条填矩阵，"最便宜的证据"这列让学生先自己判断，再让 Agent 判断一遍，对比分歧；
3. **对每个分歧追问理由**——分歧点通常就是你对这段代码理解不清的地方；
4. 明确标出至少 3 条"故意不测"，每条写理由；
5. 按"风险高 + 成本低"排序，圈出最先做的 3 条；
6. 让 Agent 检查一遍矩阵：有没有哪条高风险行为完全没被覆盖？

## 常见误区

- 矩阵不是一次做完的，先覆盖高风险，剩下的随开发补；
- 已有测试要先核对它测的是不是你以为的东西，很多老测试早就名不副实；
- 打桩（mock）会抹掉真实边界，外部服务的关键失败路径至少要有一条真实验证。

## 证据

一张完整的测试矩阵文件，含风险等级、证据层级、成本和现状；至少 3 条显式的"不测"及理由；圈出的前 3 条优先项。
