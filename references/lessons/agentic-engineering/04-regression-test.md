# 一次真实的 RED → 修复 → GREEN

## 目标

学生亲手走完一次回归测试闭环：先让测试因为**正确的原因**失败，再修，再让它通过。

## 讲授

这一节只做一件事，但它是整门课的分水岭。

**回归测试**是为一个真实发生过的 bug 写的测试。它的作用不是发现新问题，是**保证这个老问题不会再回来**。项目里每修一个 bug 就留一个回归测试，时间越久这张网越密。

顺序绝对不能变：

```text
先写测试 → 运行 → 看到它失败（RED）→ 确认失败原因就是那个 bug
→ 修复代码 → 再运行 → 看到它通过（GREEN）
```

**为什么必须先看到 RED？**因为一个从来没红过的测试，你无法确定它到底在测什么。太常见了：测试写错了断言、根本没跑到那行、或者永远返回真——修复前后都是绿的，你以为有保护，其实什么都没有。

**"因为正确的原因失败"这个限定同样重要。**测试失败可能是因为文件路径错了、依赖没装、语法错误——这些都不算。你要看到的失败信息，必须明确指向那个 bug 的行为。比如你要的是：

```text
AssertionError: expected 108.00 but got 100.00
```

而不是 `ModuleNotFoundError`。

对 Agent 要额外盯一件事：**它经常先修代码再补测试，然后告诉你"测试通过了"。**这时候的绿色毫无意义。必须要求它先写测试、先给你看红色。

常见误区：跳过 RED；Agent 说跑过了就信；修完不再跑一次完整测试（可能修坏了别的）。

## 实验

1. 从项目历史里找一个真实修过的 bug，或者现在就有的一个；
2. **先写测试**，用最小的输入复现它；
3. 运行，**把失败输出完整抄下来**——这是本节最重要的一份证据；
4. 检查失败原因：是不是那个 bug？如果是环境问题、导入错误，回去修测试本身；
5. 修复代码；
6. 再运行，看到通过，**并把退出码记下来**（`echo $?` 应该是 0）；
7. 跑一遍完整测试套件，确认没修坏别的；
8. 提交时把 bug 描述、测试和修复放在同一个 commit 里。

## 常见误区

- 直接改断言让测试变绿是最糟的操作，等于把警报关掉；
- 测试跑得慢会让人不想跑，慢的测试要拆或者标记出来单独跑；
- 一个 bug 对应一个回归测试就够了，不必为它补一套。

## 证据

RED 阶段的完整失败输出、GREEN 阶段的通过输出和退出码、修复的 diff、完整套件的运行结果。四样缺一不可——只有 GREEN 没有 RED 的记录不予认可。
