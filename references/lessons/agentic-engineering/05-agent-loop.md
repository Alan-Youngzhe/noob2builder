# 小切片、小 diff、验证、commit

## 目标

学生能把"让 Agent 改这个项目"从赌博变成可控流程：每一轮改动都小到能看懂、能验证、能回退。

## 讲授

vibe coding 阶段最爽的操作是"你帮我把这个功能做完"，最痛的时刻是它改了 15 个文件、你不知道哪个改坏了、也不敢全部回退因为里面有对的。

破解办法是把一次大改拆成一串小循环：

```text
定义这一轮的目标（一句话说得清）
→ 让 Agent 只改这一处
→ 看 diff（真的看，不是滚过去）
→ 验证（跑测试或手动确认行为）
→ commit
→ 下一轮
```

**每一轮的规模有个粗略的标准：diff 控制在两三百行以内、一句话能说清改了什么。**超过就该拆。用 `git diff --stat` 一眼就能看出来。

**看 diff 是这个循环里最不能省的一步。**Agent 经常顺手做你没要求的事：改了格式、删了它认为没用的代码、换了个"更好"的写法。这些改动混在一起，出问题时你分不清是哪个导致的。看 diff 的时候只问三个问题：**这些改动我都要吗？有没有我没要求的？有没有该改而没改的？**

**commit 是免费的回退点。**每一轮验证通过就提交，出事最多丢一轮。相反，攒了一天才提交一次，回退就是灾难。commit message 写清楚"为什么改"，不是"改了什么"——改了什么 diff 里都有。

**Agent 连续两次修不好同一个问题时，停下来。**第三次通常也不行，而且会越改越乱。正确动作是：回退到上一个 commit，重新描述问题，或者换个思路。这条止损线要提前定好，不然很容易在一个坑里陪它耗一下午。

常见误区：一次让它做完；只看它的总结不看 diff；很久才提交一次；在同一个失败上反复重试。

## 实验

用测试矩阵里排第一的那条来走：

1. 把它拆成 3 个以上的小切片，每片一句话说清目标；
2. 第一片：让 Agent 只改这一处，明确说"不要顺手改别的"；
3. `git diff` 逐行看完，把它做的**你没要求的改动**列出来；
4. `git diff --stat` 确认规模；超了就让它拆小重来；
5. 验证行为，commit；
6. 重复剩下的切片；
7. 中途故意让它遇到一次卡壳，练习"两次不行就回退"这个动作：
   ```bash
   git reset --hard HEAD
   ```
   **这条命令会丢弃所有未提交的改动，执行前必须先确认没有你要留的东西。**

## 常见误区

- "顺手优化一下"是 diff 膨胀的主要来源，明确禁止；
- commit 信息写"fix bug"等于没写；
- 拆切片本身也需要判断，拆不动的时候说明你对需求还没想清楚。

## 证据

一串小 commit 记录（`git log --oneline` 输出），每条能看出改了什么、为什么；至少一轮的完整 diff 审查记录，含"它做了我没要求的事"的具体条目；至少一次触发止损线并回退的记录。
