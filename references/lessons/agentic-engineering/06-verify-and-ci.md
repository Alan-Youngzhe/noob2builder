# 一条 verify 命令，和一道机器门禁

## 目标

学生给项目做出一条能一次跑完所有检查的命令，并把它接进 CI，让"能不能合并"由机器判断而不是由人的记性判断。

## 讲授

**问题**：项目上的检查越来越多——类型检查、lint、单元测试、构建。每次改完要跑哪几条？靠记。记漏了就出事。

**解法**：把它们合成一条命令。名字叫什么不重要，叫 `verify` 是本校的约定：

```json
{
  "scripts": {
    "verify": "npm run typecheck && npm run lint && npm test && npm run build"
  }
}
```

`&&` 是关键：前一条失败就不往下走，整条命令的退出码非 0。于是**判断项目健不健康只剩一个动作**：跑 `npm run verify`，看 `echo $?` 是不是 0。

这条命令的价值远超省事：

- **给你**：改完跑一次，不用记要跑什么；
- **给 Agent**：可以让它每轮自己跑一次，失败了自己看错误——这是让它自主工作的前提；
- **给 CI**：机器门禁跑的就是这一条。

**接进 CI** 就是让每次 push 和 PR 自动跑一遍。GitHub Actions 的配置放在 `.github/workflows/` 下，一个最小的样子是：

```yaml
name: verify
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run verify
```

具体 action 版本和 Node 版本以现场查证为准。

**CI 最大的价值不是跑测试，是"跑在一台干净的机器上"。**你本地能过、CI 过不了，十有八九是你依赖了本地才有的东西——某个全局安装的包、某个只有你有的环境变量、某个没提交的文件。这类问题在本地永远发现不了。

**门禁要真的挡住。**在 GitHub 仓库设置里把这个检查设为必须通过才能合并，否则它就只是个装饰。红了就修，不要养成"红着也合"的习惯——一旦开了这个口子，CI 就废了。

常见误区：verify 里塞太多导致跑十分钟没人愿意跑；CI 红了直接合；本地和 CI 用不同的命令。

## 实验

1. 列出项目现在所有的检查命令；
2. 合成一条 `verify`，本地跑通，确认退出码为 0；
3. **故意制造一个失败**（改坏一个类型或断言），确认 verify 真的红了、退出码非 0——没验证过会失败的门禁不算门禁；
4. 写 CI 配置，push，看它在 GitHub 上真的跑起来；
5. 提一个故意会失败的 PR，确认 CI 挡住了它；
6. 在仓库设置里把这个检查设为合并必需；
7. 记录 verify 的耗时，超过 5 分钟就考虑拆快慢两档。

## 常见误区

- `npm install` 和 `npm ci` 不一样，CI 里用后者才能保证依赖版本一致；
- 本地过 CI 不过时，先怀疑环境差异，别急着改代码；
- 门禁不是越严越好，慢到让人绕开的门禁等于没有。

## 证据

`verify` 命令定义；本地成功和**失败**两次的输出与退出码；CI 配置文件；GitHub 上真实的一次绿色运行和一次红色拦截截图或链接；分支保护已开启的确认。
