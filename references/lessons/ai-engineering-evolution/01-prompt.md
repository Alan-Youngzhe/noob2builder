# 第一层：Prompt 能解决什么，不能解决什么

## 目标

学生能判断一个任务失败是不是"提示词没写好"的问题，并知道提示词能力的天花板在哪。

## 讲授

这门课用**同一个真实任务**贯穿五层。先选好它——从学生自己的工作里挑一件重复做的事，比如"把客户发来的需求邮件整理成结构化工单"。后面每一层都拿它加工。

**Prompt 层解决的是：把你的意图表达成模型更容易完成的输入。**

有效的动作就四个，而且顺序有讲究：

1. **给角色和目标**——"你是一个把需求邮件整理成工单的助手"，比直接下命令更能框定输出风格；
2. **给输出格式**——最有效的一条。要 JSON 就给出字段和一个真实样例，别只说"结构化输出"；
3. **给例子**（few-shot）——一到三个输入输出对，比十句形容词管用。这是提升准确率性价比最高的动作；
4. **拆步骤**——复杂任务让它先列步骤再执行，中间过程可见了，错在哪一步也就看得见了。

**天花板在哪：**

- 它**不知道**的事，提示词写得再好也变不出来（要 Context 层）；
- 它**做不到**的事，比如读你本地的文件，提示词解决不了（要工具）；
- 它**这次对了下次错**，提示词解决不了稳定性（要 Harness 和 Loop）。

有一条经验值得直说：**当你开始给提示词加"请务必""一定要""非常重要"这类强调词的时候，通常说明这个问题已经不是提示词能解决的了。**强调能小幅提高概率，但你真正需要的是把这个要求变成一个可以检查的东西。

常见误区：把所有失败都归因于提示词；提示词越写越长（长到几百行时互相冲突，效果反而下降）；抄别人的"万能模板"而不看自己任务的特点。

## 实验

1. 选定贯穿全课的那个真实任务，准备 5 个真实输入样本；
2. **基线**：用一句最朴素的话让 Agent 做，5 个样本各跑一次，记录正确率；
3. 只改提示词——加角色、加输出格式、加两个例子、拆步骤——再跑同样 5 个样本；
4. 记录两次的正确率对比，以及**剩下的错误分别是什么类型**；
5. 把剩余错误分类：属于"它不知道"、"它做不到"，还是"它不稳定"？这三类分别对应后面三层；
6. 保存这份基线数据，后面每一层都要和它对比。

## 常见误区

- 只跑一次不能说明问题，同一个样本至少跑两三次看稳定性；
- 正确率要有明确判定标准，"感觉还行"不是数据；
- 例子要用真实数据，编的例子会把模型带偏。

## 证据

一份基线记录：任务描述、5 个真实样本、朴素提示词的正确率、优化后的正确率、剩余错误的分类。这份文件后面四节课都要用。
