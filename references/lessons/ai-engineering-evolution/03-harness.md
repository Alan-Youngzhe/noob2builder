# 第三层：Harness 让环境替你守规矩

## 目标

学生能把"希望它记得做的事"变成"环境强制它做的事"，理解为什么 Claude Code 这类工具的能力很大一部分来自 Harness 而不是模型。

## 讲授

上一节分出来的第三类错误——**它不稳定**——从这一层开始管。

**Harness（直译是"挽具"）指模型周围的那套运行环境**：规则文件、可用命令、权限设置、验证脚本、失败后怎么恢复。它解决的问题是：**不要指望模型记住，让环境来保证。**

对比两种做法：

| 靠提示词 | 靠 Harness |
|---|---|
| "改完代码记得跑测试" | 提交前钩子自动跑 `verify`，失败就拒绝 |
| "不要删除重要文件" | 权限配置里禁止删除，删除需要人工确认 |
| "输出必须是合法 JSON" | 输出后用校验器检查，不合法就自动重试 |
| "遵守项目代码风格" | lint 和格式化工具自动执行 |

左边是**概率**，右边是**保证**。模型再强，左边也只能提高概率。

Claude Code 就是一个很好的 Harness 实例，你可以直接拆开看：

- `CLAUDE.md` —— 规则注入；
- `~/.claude/settings.json` 里的 permissions —— 权限控制；
- hooks —— 在特定事件（如工具执行前后）自动运行你指定的命令；
- Skill —— 按任务加载的做法说明。

**同一个模型，放在一个好 Harness 里和一个裸的聊天框里，表现差距可能非常大。**近几年 Agent 能力的提升，相当一部分来自这一层，而不只是模型本身变强了。

**Harness 的核心零件是验证器**——一个能自动判断"对不对"的东西。有了它，后面的 Loop 层才可能存在。验证器可以是测试、schema 校验、lint，也可以是另一个模型按你的判断标准打分。

常见误区：用越来越长的提示词代替验证器；把 Harness 理解成"更复杂的提示词"；以为装了很多工具就是好 Harness（没有验证的工具只是更多出错的机会）。

## 实验

继续用那个任务：

1. 拿出上一节写的判断标准文件，把它改写成**可以被机器检查**的形式——比如 JSON Schema、必填字段检查、取值范围校验；
2. 写一个验证脚本，输入一条输出，返回通过或不通过以及原因；
3. 用这个验证器检查前两节所有的输出，看它和你的人工判断一致率有多高；
4. 不一致的地方分析：是验证器太松、太严，还是你的人工判断本身有问题？
5. 把验证器接到流程里：模型输出后自动校验，不通过就把错误信息反馈给它重试一次；
6. 跑同样 5 个样本，记录正确率和平均重试次数。

## 常见误区

- 验证器本身也需要被验证，第 3 步不能省；
- 不是所有东西都能被机器检查，"语气是否得体"这类的就需要别的办法，别硬写；
- 重试次数要有上限，否则会陷入死循环。

## 证据

一份可执行的验证脚本；验证器与人工判断的一致率；接入验证后的正确率、重试次数，与前两层的对比。
