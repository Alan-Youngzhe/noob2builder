# 第五层：Graph 和多 Agent，多数时候你不需要

## 目标

学生能判断一个任务是否真的需要显式编排多个节点，并能识别"画成图""多 Agent 协作"什么时候只是包装。

## 讲授

**Graph 解决的是：多个步骤之间有明确的依赖关系、共享状态、各自需要不同的验证方式时，把它们显式画出来并编排。**

真正需要 Graph 的信号有三个，要同时出现：

1. **步骤之间有分支和汇合**——根据中间结果走不同路径，最后再合起来；
2. **不同步骤需要不同的验证器**——比如提取信息用 schema 校验，写文案用另一个模型打分；
3. **状态需要在步骤间精确传递**——前一步的结构化输出是后一步的输入，不能靠自然语言模糊交接。

常见的编排工具有 LangGraph 等，具体选型以现场查证为准。它们提供的核心能力是：节点、边、共享状态、检查点（可以从中间某一步恢复）。

**什么时候是包装：**

- **一条直线的流程**，A 做完 B 做，B 做完 C 做——这就是一个函数调用序列，画成图不增加任何能力；
- **"多个 Agent 讨论"**——让三个 Agent 分别扮演产品经理、工程师、测试员互相对话。听起来很高级，实际上它们共享同一个模型的同一套偏见，讨论出来的结论不比一个 Agent 好多少，成本是三倍；
- **没有验证器的多节点**——每个节点都不知道自己做得对不对，错误会沿着图一路传下去并被放大。

**多 Agent 真正有价值的场景很具体**：一是**隔离上下文**——主线太长了，派一个 Subagent 去干一段独立的活，它带回结论不带回过程，主线保持干净；二是**并行**——几件互不依赖的事同时做。这两条都是工程收益，不是"集体智慧"。

**本课的核心判断落在这里：复杂度要被需求证明。**每加一层，都要能指出"上一层解决不了的具体问题是什么"。指不出来，就是包装。

常见误区：把流程图画得越复杂越显得专业；以为多 Agent 讨论能提升质量；在还没做好单个 Agent 的时候就上编排框架。

## 实验

继续用那个任务：

1. 把目前的流程画出来——大概率是一条直线；
2. 逐条检查三个信号：有分支汇合吗？需要不同验证器吗？有需要精确传递的结构化状态吗？
3. 如果三个信号都没有，**结论就是"不需要 Graph"**，写下理由，跳到第 6 步；
4. 如果确实有，只把真正需要分支的那一段做成 Graph，其它保持线性；
5. 对比做成 Graph 前后的正确率、成本和调试难度；
6. 附加题：让 Agent 用"三个角色讨论"的方式做一次同样的任务，和单个 Agent 的结果对比，看质量差距和成本差距。

## 常见误区

- 得出"不需要 Graph"不是没完成实验，是完成得最好的结论之一；
- 附加题的讨论结果如果看起来更好，要问：是真的更好，还是只是更长？
- 编排框架的学习成本是真实成本，要算进去。

## 证据

流程图、三个信号的逐条判断和结论；如果做了 Graph，前后对比数据；附加题的多 Agent 对比结果。
