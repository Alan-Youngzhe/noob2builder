# MCP、Skill、Plugin、规则文件、Subagent 各管什么

## 目标

学生能分清这几个高频词各自解决什么问题，知道该往哪加东西，并且不再见到什么装什么。

## 讲授

这几个词经常被混着用，其实分工很清楚。**MCP 给的是能力，Skill 给的是做法，规则文件给的是约束。**

| 名字 | 实体是什么 | 解决什么问题 | 装在哪 |
|---|---|---|---|
| **Tool / Function Calling** | 一个可调用的动作 | 让模型能操作外部世界 | 由宿主或 MCP 提供 |
| **MCP**（Model Context Protocol） | 一个对接外部服务的协议 | 接新服务不用每次重写对接 | `~/.claude/settings.json` 或 `.mcp.json` |
| **Skill** | 一份 Markdown 说明书 | 让 Agent 在特定任务上按既定方法做 | `~/.claude/skills/<名字>/SKILL.md` |
| **Plugin** | 一个打包分发单元 | 把 Skill、命令、MCP 配置一起装 | 通过插件市场安装 |
| **规则文件** | `CLAUDE.md` | 固定的偏好和红线 | 全局或项目根目录 |
| **Subagent** | 一个独立上下文的分身 | 隔离上下文、并行处理 | 由主 Agent 调度 |

判断该加哪个，问自己一句话：

- 它**做不到**某件事（连不上你的数据库、访问不了某个系统）→ 缺**能力**，加 MCP；
- 它**做得到但做得不对**（每次都用你不喜欢的方法）→ 缺**做法**，写 Skill；
- 它**反复犯同一个小毛病**（老是用英文回复、老是直接推主干）→ 缺**约束**，写进 `CLAUDE.md`；
- 主线**上下文被撑爆**、或者有几件独立的活可以并行 → 用 **Subagent**。

**Skill 就是 Markdown，不是程序。**你现在上的这门课就是一个 Skill：它没给 Agent 任何新工具，只是规定了它怎么教你。这也意味着你自己就能写一个——不需要会编程。

反向的代价必须说清楚：**装的东西不是免费的。**每个 MCP 的工具描述都要占 Context，装十个 MCP 可能几千 token 就没了，而且工具多了模型更容易选错。规则文件同理，写得又长又互相打架时，行为会变得难以预测。

常见误区：见到好用的 MCP 就装；把 Skill 当插件程序；以为规则写得越细越可控（太细会让它僵化在你没想到的场景上）。

## 实验

1. 用 `/mcp` 或等价方式列出当前接入的 MCP，逐个说出提供了什么能力，找出你其实从没用过的；
2. 打开 `~/.claude/skills/` 随便看一个 Skill 的 `SKILL.md`，确认它就是纯文本；
3. 拿本校的 `SKILL.md` 对照上表，指出它属于哪一类、为什么不是 MCP；
4. 找一个你自己反复纠正 Agent 的小毛病，写进 `~/.claude/CLAUDE.md`，新开会话验证是否改善；
5. 在 `MY_AI_MAP.md` 里加一节：我装了什么、各解决什么问题、哪些可以卸掉。

## 常见误区

- MCP 装了不用也在占 Context，定期清理；
- Skill 的触发靠它的 `description` 写得准不准，写模糊了就不会被调起来；
- Subagent 看不到主线上下文，交给它的任务必须自带完整交代。

## 证据

`MY_AI_MAP.md` 中有一份真实的清单：已装的 MCP、Skill、规则文件各是什么、解决什么问题；至少完成一次"发现毛病 → 写进规则 → 新会话验证"的闭环，并至少识别出一个可以卸掉的东西。
