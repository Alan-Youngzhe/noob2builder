# 画 Context Map：你的产品到底知道什么

## 目标

学生能为一个 AI 产品画出完整的 Context Map，并在画的过程中发现哪些数据拿不到、哪些不该拿、哪些会过期。

## 讲授

上一节说产品的价值在模型之外的 Context。这一节把它画出来。

**Context Map 的每一条数据都要回答六个问题：**

| 维度 | 要回答的问题 | 画不出来意味着什么 |
|---|---|---|
| **来源** | 从哪来？用户输入、系统读取、第三方接口？ | 这条数据你可能根本拿不到 |
| **更新** | 多久变一次？谁来更新？ | 你会用过期信息做判断 |
| **权限** | 用户授权了吗？谁能看？ | 合规风险，或者用户不敢用 |
| **时效** | 多久之后就不可信了？ | 模型会自信地引用过期事实 |
| **噪声** | 里面有多少无关或错误的内容？ | 注意力被稀释，回答质量下降 |
| **删除** | 用户要求删除时，能删干净吗？ | 法律风险，也是信任问题 |

最容易被跳过的是最后一条。**用户说"把我的数据删掉"，你能保证它从数据库、向量库、日志、缓存、备份里全部消失吗？**大部分早期 AI 产品答不上来，因为设计时根本没想过。

**画这张图最大的价值不是整理，是暴露问题。**你通常会发现：

- 最有价值的那份数据，你其实拿不到（在别人的系统里、没有接口、用户不愿给）；
- 你以为能拿到的数据，时效性很差，一周前的就已经不准了；
- 有一份数据你拿到了，但其实不该拿——超出了用户授权的范围。

这三类发现，每一个都可能直接改变产品方向。

一个具体例子：一个"帮销售写跟进邮件"的 AI 产品。最有价值的 Context 是**这个客户之前说过什么、卡在哪个阶段、决策人是谁**——这些在 CRM 里、在邮件往来里、在销售自己脑子里。如果只能拿到用户手动粘贴的一段话，这个产品和通用聊天框就没有区别。

常见误区：只列"需要什么数据"不问"能不能拿到"；忽略删除和时效；把"用户可以手动上传"当成数据来源方案（大部分用户不会）。

## 实验

1. 选一个产品：上一节拆过的，或你自己的想法；
2. 列出它需要的所有 Context，至少 5 条；
3. 每一条都填完六个维度，**填不出来的格子不许空着，写"不知道"**；
4. 标出三类问题：拿不到的、会过期的、不该拿的；
5. 让 Agent 扮演一个挑剔的用户，针对"权限"和"删除"两列提问，看你答不答得上；
6. 基于发现写一段话：这张图改变了你对这个产品的什么判断？

## 常见误区

- 第 3 步写"不知道"比编一个答案有价值得多；
- 涉及个人信息和客户数据时，先读 `../shared/safety-and-secrets.md`；
- 画完没有任何发现，通常说明画得不够诚实。

## 证据

一张完整的 Context Map（至少 5 条数据 × 6 个维度），标出三类问题；第 5 步的问答记录；第 6 步的判断变化说明。
