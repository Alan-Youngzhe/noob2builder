# 这件事为什么不能放前端

## 目标

学生能对着自己项目里的任意一个功能，判断它该放前端还是后端，并说出依据——而不是靠感觉。

## 讲授

先读 `../shared/web-product-foundations.md` 的链路图。这里只解决一个判断：**边界画在哪。**

前端跑在**用户的机器上**，这句话是所有判断的起点。用户能打开 DevTools 看你的代码、改你的变量、伪造你的请求。所以凡是"用户不该能改的"，就不能只放前端。

四条硬标准，中任意一条就必须有后端：

1. **秘密**——API Key、数据库密码、第三方凭证。前端代码是公开的，写进去等于贴在门口。哪怕你用了打包工具，`curl` 一下你的 JS 文件就能看到；
2. **权限**——"只有管理员能删"这种规则，放前端只是把按钮藏起来了，接口本身还在，谁都能直接调；
3. **持久化**——数据要在换设备、换浏览器、清缓存之后还在；
4. **共享**——两个用户要看到同一份数据。

反过来，**只影响这一个人这一次操作**的事，放前端更快更好：折叠展开、表单的即时格式提示、纯展示的排序筛选。

必须记牢的一条：**前端校验不算安全，它只算体验。**手机号格式在前端提示是为了让用户少填错一次；但后端必须再验一遍，因为绕过前端直接发请求太容易了——`curl -X POST` 一行的事。

一个具体例子：一个"我的待办"应用。勾选时立刻变灰是前端（体验）；这条待办属于谁、能不能被别人看到、换台电脑还在不在，全是后端（权限 + 持久化 + 共享）。

常见误区：以为把变量名改得难懂就藏住了秘密；以为按钮隐藏了功能就关闭了；以为 `localStorage` 是持久化（它只在这一个浏览器里）。

## 实验

拿学生自己的项目或一个真实网站做：

1. 打开 DevTools 的 Network 面板，点一个按钮，看它到底发了什么请求：方法、地址、请求体；
2. 打开 Sources 面板，找到前端的 JS 文件，确认这些代码你完全看得见；
3. 让 Agent 用 `curl` **绕过页面**，直接把第 1 步的那个请求重发一次，看服务端认不认——这一步是本节的核心，它当场证明"前端不是防线"；
4. 把学生项目里的功能逐条列出来，用上面四条标准分类：前端 / 后端 / 两边都要；
5. 画出这个项目的链路图：用户动作 → 前端 → API → 数据。

## 常见误区

- "反正没人会去看"不是理由，自动扫描工具每天都在扫；
- 前端和后端可以是同一个人写、同一个仓库，但仍然是两个信任级别；
- 静态页面（纯展示、无登录、无数据）确实不需要后端，别为了架构而架构。

## 证据

一张链路图，加一份功能分类表，每条都写了归属理由。第 3 步的 `curl` 结果入档——无论服务端是拒绝了还是接受了，两种结果都要如实记录并解释。
