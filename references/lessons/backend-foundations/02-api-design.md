# 先约定接口，再写实现

## 目标

学生能读懂和设计一个 REST 风格的接口，说清一个请求由哪几部分组成，并让 Agent 先写接口约定再动手实现。

## 讲授

**API 是前后端之间的合同。**先签合同再施工，两边可以同时开工；先施工后补合同，改一次动两边。

一个 HTTP 请求由四部分组成：

```text
POST /api/todos          ← 方法 + 路径
Content-Type: application/json
Authorization: Bearer xxx    ← 请求头
{ "title": "买菜", "done": false }   ← 请求体
```

**方法**表达动作，路径表达资源。常用就这几个：

| 方法 | 干什么 | 例子 | 重复调用安全吗 |
|---|---|---|---|
| `GET` | 取数据 | `GET /api/todos` | 安全 |
| `POST` | 新建 | `POST /api/todos` | 不安全，会建出多条 |
| `PUT` | 整体替换 | `PUT /api/todos/7` | 安全 |
| `PATCH` | 局部修改 | `PATCH /api/todos/7` | 通常安全 |
| `DELETE` | 删除 | `DELETE /api/todos/7` | 安全 |

最后一列（幂等性）是实战里最常被忽略的：用户网络卡了狂点三次提交，`POST` 会建出三条数据。所以创建类接口要么加去重键，要么在前端锁按钮，两者最好都做。

**路径用名词复数、不用动词**：`GET /api/todos/7` 而不是 `/api/getTodo?id=7`。动作已经由方法表达了，路径再表达一次就是重复。

**响应**要有稳定结构。成功返回什么、失败返回什么，两边都要约定死：

```json
{ "id": 7, "title": "买菜", "done": false, "createdAt": "2026-09-10T08:00:00Z" }
```

失败时不要返回 `200` 加一句 `{"error": "..."}`。用状态码表达结果，这是 HTTP 本来就有的机制：`201` 创建成功、`400` 参数不对、`401` 没登录、`403` 没权限、`404` 不存在、`409` 冲突、`500` 服务端炸了。详见 `../shared/http-status-codes.md`。

**给 Agent 干活的正确顺序**：先让它输出接口约定（路径、方法、请求体、响应体、错误码），你过一遍，再让它实现。跳过这一步，你会在实现完之后才发现字段名跟前端对不上。

常见误区：所有接口都返回 `200`；路径里塞动词；一个接口返回的字段时有时无；把分页、排序、筛选做成一堆独立接口而不是查询参数。

## 实验

1. 从学生项目里挑一个真实功能，**先只写接口约定**，不写任何实现代码；
2. 让 Agent 挑毛病：方法选得对吗？幂等吗？错误码全吗？字段命名一致吗？
3. 用 `curl -i` 手动构造这个请求（服务还没实现也没关系，先看请求长什么样）；
4. 实现之后，用 `curl -i` 跑三次：一次成功、一次参数错误、一次访问不存在的资源，逐个核对返回的状态码是不是约定的那个；
5. 故意重复发送三次创建请求，看会不会产生三条数据——如果会，讨论怎么解决。

## 常见误区

- 约定写在聊天记录里等于没写，落到文件里；
- 返回体里混入内部实现细节（数据库字段名、堆栈信息）会泄露信息也会绑死实现；
- 时间统一用 ISO 8601 加时区，别用各地格式的字符串。

## 证据

一份接口约定文件，加上第 4 步三次 `curl -i` 的真实输出（含状态码和响应体）。第 5 步的重复提交结果如实记录，包括"确实建出了三条"这种不好看的结果。
