# 选一个服务端方案，并说出为什么

## 目标

学生能让 Agent 基于自己的真实情况提出方案，自己听懂利弊并拍板——而不是被塞一个技术栈。

## 讲授

本校不指定技术栈。但"你自己选"对小白是空话，除非你知道在比什么。所以先给判断维度，再给一条默认路径。

**主流选项和它们的实际差别：**

| 方案 | 语言 | 适合什么 | 一句话特征 |
|---|---|---|---|
| Express | Node.js | 通用、生态最大 | 老牌，教程和示例最多 |
| Fastify | Node.js | 同上，更看重性能 | 更快，内置校验 |
| Hono | Node.js/边缘 | 部署到边缘平台 | 轻，跨运行时 |
| FastAPI | Python | 数据、AI、脚本类后端 | 自动生成接口文档，类型友好 |
| Flask | Python | 极小的服务 | 最简单，功能也最少 |

**选的时候只看四条：**

1. **你的项目已经在用什么语言？**前端是 JS/TS 的话，后端用 Node 系可以共用类型定义和一套依赖管理，省事最多；
2. **要不要接 AI、数据处理或现成的 Python 库？**要，就用 Python 系，别为了统一语言硬扛；
3. **打算部署到哪？**目标平台原生支持什么，就用什么，能省掉一堆配置；
4. **出问题时能不能找到答案？**生态大小直接决定你和 Agent 排错的效率。

**给小白的默认路径**：前端是 TypeScript → Express 或 Fastify；主要做数据/AI 相关 → FastAPI。两条都选不出来的时候，选 Express，因为遇到问题最容易搜到答案。

**让 Agent 提方案的正确姿势**——不要问"我该用什么框架"，要给它约束：

> 我的项目是 X，前端用 Y，需要做 Z，打算部署到 W，我的水平是 V。
> 给两个方案，说明各自的优势、劣势、上手成本，以及如果选错了迁移贵不贵。
> 推荐一个，说明理由。

最后那句"迁移贵不贵"是关键。**在早期，选错的代价远比选对的收益重要。**一个能三天内换掉的选择，不值得纠结三天。

常见误区：按热度选；一上来就上微服务、Docker、消息队列；以为选了框架就绑死了（早期项目代码量小，换框架经常只要一两天）。

## 实验

1. 把上面那段模板填成你自己的情况，发给 Agent；
2. 拿到两个方案后，**逐条追问依据**：这个"性能更好"有数据吗？这个"生态更大"体现在哪？让它区分事实和推测；
3. 让 Agent 用两个方案分别写出同一个最小接口（比如 `GET /api/health` 返回 `{"status":"ok"}`），对比代码量和启动方式；
4. 真的把其中一个跑起来，用 `curl -i http://localhost:<端口>/api/health` 拿到 `200`；
5. 写下你的选择和理由，包括"如果三个月后要换，代价大概是什么"。

## 常见误区

- Agent 的推荐往往偏向教程最多的选项，这不一定是最适合你的，要追问；
- 版本号和安装命令会变，以官方文档现场查证为准；
- 第 4 步跑不起来时先分层排查（见 `../computer-network/06-layered-diagnosis.md`），别直接换框架。

## 证据

一份选型说明：候选方案、四条维度的对比、最终选择、理由、迁移成本估计。第 4 步的真实 `curl` 输出入档，含状态码和响应体。
