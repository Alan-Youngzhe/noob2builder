# 数据存哪：先画权威源，再选工具

## 目标

学生能画出自己项目的数据权威源和访问链路，从最简方案起步，并用跨入口、跨重启的真实读写来验证。

## 讲授

先读 `../shared/database-and-data-authority.md`。这里只强调一件事：**先回答"这份数据的唯一权威源在哪"，再回答"用什么数据库"。**顺序反了就会出 Ordine 那类事故——两个进程各自建了一个数据库实例，接口 A 写进去，接口 B 读不到，`200` 全绿但数据是错的。

**按需求爬台阶，不要一步登天：**

| 方案 | 什么时候够用 | 什么时候不够 |
|---|---|---|
| 内存变量 | 原型演示，重启丢光 | 任何要留住的数据 |
| JSON 文件 | 单进程、数据量小、结构简单 | 并发写会互相覆盖 |
| SQLite | 单机、单进程写，绝大多数小项目 | 多进程同时写、多机部署 |
| PostgreSQL | 多进程、多机、需要并发和事务 | 小项目会显得重 |

**SQLite 是小项目被严重低估的答案。**它就是一个文件，不用装服务、不用配连接，一个几百人用的工具站完全扛得住。真的遇到"多个进程要同时写"或者"要部署到多台机器"，再升级到 PostgreSQL——那时候你也已经知道为什么了。

**三个必须当场想清楚的问题：**

1. **数据文件在哪？**用相对路径的话，从不同目录启动服务会落到不同文件上——这就是权威源分裂最常见的成因。用绝对路径或明确的配置项；
2. **谁能写？**只有一个进程写，还是多个入口都能写？多个的话它们连的是不是同一个库；
3. **重启之后还在吗？**很多部署平台的文件系统是临时的，重启就清空，SQLite 文件会一起没。这一条必须在部署前确认。

常见误区：把数据库选型当成技术品味问题；一上来就上 PostgreSQL + ORM + 迁移工具；以为写进去了就等于存下来了（没验证过重启）。

## 实验

1. 画出项目的数据流图：哪些入口会写、哪些会读、数据的唯一权威源在哪；
2. 让 Agent 基于这张图推荐方案，并说明"如果以后要升级，迁移路径是什么"；
3. 用最简方案实现一个真实的写入和读取；
4. **跨入口验证**：从接口 A 写一条，从接口 B（或直接用数据库命令行）读出来，确认是同一条；
5. **跨重启验证**：停掉服务，重新启动，再读一次，确认数据还在；
6. 故意从另一个目录启动一次服务，观察会不会连到另一个数据文件——这一步是为了让你亲眼见到权威源分裂长什么样。

## 常见误区

- `HTTP 200` 不能证明数据真的写进去了，必须独立读一次；
- Agent 说"已经存好了"不算证据，第 4、5 步才算；
- 备份不是可选项，哪怕只是定期复制一份 SQLite 文件。

## 证据

一张数据流图，标明唯一权威源；第 4、5 步的真实读写记录（命令 + 输出）；第 6 步的现象记录——如果确实连到了不同文件，把这个结果原样写进证据，它比讲十遍都管用。
