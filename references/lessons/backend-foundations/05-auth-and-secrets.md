# 登录、权限和密钥是三件事

## 目标

学生能分清认证和授权，知道密钥该放哪、绝不能放哪，并亲手验证一次"没权限的人真的调不动"。

## 讲授

先读 `../shared/safety-and-secrets.md`。这里把三件经常被搅在一起的事拆开：

- **认证（Authentication）**：你是谁。登录、Token、验证码解决的是这个；
- **授权（Authorization）**：你能干什么。同样是登录用户，A 能删自己的数据，不能删 B 的；
- **密钥（Secrets）**：程序访问外部服务的凭证。跟用户没关系，是你的程序自己的身份。

对应的状态码正好把前两件事分开了：**`401` 是"你没登录"，`403` 是"你登录了但不许"。**返回错了会让前端做错反应——`401` 通常该跳登录页，`403` 不该。

**密钥的三条铁律：**

1. **不进前端。**前端代码用户全看得见，打包压缩也没用。需要调第三方 API，让前端请求你的后端，后端再拿着密钥去调；
2. **不进 Git。**写进 `.env`，把 `.env` 加进 `.gitignore`，同时提交一份 `.env.example` 只写键名不写值。已经提交过的密钥，删掉文件不够，**必须去服务商后台吊销重发**——Git 历史里还留着；
3. **不进聊天记录和截图。**这是实际泄露最多的途径，不是被黑。

**授权的实现原则只有一句：每个接口都要独立检查。**不要指望"前面已经检查过了"。典型漏洞长这样——`GET /api/todos/7` 检查了登录，但没检查这条 todo 是不是当前用户的，于是把 7 改成 8 就能看别人的数据。这类问题有个名字叫 IDOR（不安全的直接对象引用），是小项目最常见的真实漏洞，没有之一。

常见误区：把权限判断只写在前端（隐藏按钮）；用 `NEXT_PUBLIC_` 之类的前缀暴露了本该保密的变量；以为自己的小项目没人会攻击（扫描器不挑）。

## 实验

1. 检查项目里所有密钥的位置，确认 `.env` 在 `.gitignore` 里，且历史提交里没有密钥：
   ```bash
   git log -p | grep -iE "api[_-]?key|secret|password|sk-" | head
   ```
2. 给一个接口加上登录检查，用 `curl -i` 不带 Token 请求一次，确认拿到 `401`；
3. 用 A 用户的 Token 去访问 B 用户的资源，确认拿到 `403` 或 `404`——**这一步是本节最重要的实验**，绝大多数小项目在这里是漏的；
4. 如果第 3 步真的返回了 B 的数据，把这个结果原样记下来，然后修复，再验证一次；
5. 检查前端打包产物里有没有密钥：
   ```bash
   grep -rE "sk-|api[_-]?key" dist/ 2>/dev/null | head
   ```

## 常见误区

- 密码不能明文存，用成熟的哈希方案，别自己发明；
- Token 要有有效期，永不过期的 Token 泄露一次就永久有效；
- 认证和授权都要在**后端**做，前端那份只是体验优化。

## 证据

第 2、3 步的真实 `curl -i` 输出，含状态码；越权测试的结论明确写出来——通过了写通过，漏了就写漏了并附修复后的复测。密钥检查命令和输出入档。
