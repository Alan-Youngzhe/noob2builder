# 部署：让别人真的能打开

## 目标

学生把服务部署到一个真实可访问的地址，用另一台设备验证成功，并知道出问题时去哪看日志。

## 讲授

这是 ⑧ 那节"本地能跑不等于别人能访问"的收尾。要让外人访问，你需要四样东西：**一个公网地址、一个长驻的进程、正确的环境变量、以及能看到日志的地方。**

**前端和后端的部署不是一回事**，这是小白最容易卡住的地方：

- 前端通常构建成一堆静态文件（`npm run build` 产出 `dist/` 或 `.next/`），部署就是把这些文件放到 CDN 上，没有进程；
- 后端是一个**长驻进程**，必须一直活着监听端口，挂了要能自动重启。

常见平台各有侧重，以现场查证当前情况为准：Vercel 和 Netlify 偏前端与无服务器函数；Railway、Render、Fly.io 适合长驻的后端进程；云厂商的虚拟机最灵活也最需要你自己管。

**四个几乎人人都会踩的坑：**

1. **端口不能写死。**平台会通过环境变量告诉你监听哪个端口，代码里要读 `process.env.PORT`（Node）或等价物，写死 `3000` 会启动失败；
2. **必须监听 `0.0.0.0`，不能是 `127.0.0.1`。**后者只接受本机连接，在容器里等于谁都连不上；
3. **环境变量要在平台上重新配一遍。**你本地的 `.env` 不会被上传（它在 `.gitignore` 里，这是对的），平台上的配置界面得手动填；
4. **文件系统可能是临时的。**很多平台重启就清空，SQLite 文件会一起没。有持久化需求就要挂载卷或改用托管数据库。

**日志是你唯一的眼睛。**本地你能看终端，线上只能看平台的日志面板。部署前就该确认：日志在哪看、报错会不会被吞掉。

常见误区：以为部署成功就等于功能正常（构建通过 ≠ 接口能用）；只在自己电脑上验证过；把生产环境的数据库连到本地。

## 实验

1. 部署前自检：端口读环境变量了吗？监听 `0.0.0.0` 了吗？`.env` 没进 Git 吧？
2. 部署，拿到公网地址；
3. **用 `curl -i` 打线上地址**，确认核心接口返回预期状态码——不要只在浏览器里看首页；
4. **换一台设备、换一个网络**（手机流量，不连 Wi-Fi）打开，确认外人真的能访问；
5. 故意触发一次错误（请求一个不存在的路径），去平台日志面板找到这条记录，确认你能看见；
6. 如果有数据：写一条数据，**重启服务**，再读一次，确认没丢。

第 4 步没有第二台设备时标记为**演练**，存档写 `simulated`，不能写成验证通过。

## 常见误区

- 部署平台的免费额度常有休眠策略，第一次访问会很慢，这不是你的 bug；
- HTTPS 证书大多由平台自动处理，自己搭服务器才需要操心；
- 线上出问题先看日志再改代码，别盲改重新部署——每次部署都要等构建。

## 证据

一个真实可访问的公网地址；第 3 步的 `curl -i` 输出；第 4 步的跨设备验证结果（截图或如实标记为演练）；第 5 步在日志里找到的那条错误记录；有数据的项目还要有第 6 步的重启前后对比。
