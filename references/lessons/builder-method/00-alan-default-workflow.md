# Alan 默认 0→1 Builder 工作流

## 目标

让学生先看见一条真实、可复用的项目主干，再根据自己的项目从任意节点进入。

## 主流程

```text
brainstorming 发散探索
→ GrillMe 需求访谈与收敛
→ PRD v0
→ Design System
→ Lovable 原型
→ 反写 PRD v1
→ AI 产出 Spec
→ 敏捷 MVP
→ 可行性门
→ 工程质量 + 测试 + 跨模型 Review
→ 正式发布与反馈
```

### 1. brainstorming → GrillMe → PRD v0

先用 brainstorming 在有限时间内发散用户、问题、场景和可能方向，保留多个候选但不急着选技术。再用 GrillMe 一次只解决一个会改变需求的问题，收敛用户、场景、输入输出、范围、成功标准和边界。技术细节交给 Agent。收敛结束产出薄 PRD v0，它是原型探索的起点，不是假装一切已经确定。

### 2. Design System → Lovable

先确定产品语气、颜色角色、字号层级、间距、圆角、组件和关键交互状态，让 Lovable 得到一致的视觉与交互约束；再生成第一版可见原型。

### 3. 原型 → PRD v1 → Spec

学生真实查看原型，标出保留、删除、修改和新增。Agent 把这些决策反写为 PRD v1，再结合 PRD、Design System 和原型产出 Spec。原型用于发现需求，不自动等于生产代码。

PRD v1 要通过独立交接测试：给一个没参加需求讨论的开发者或 Agent，只提供 PRD v1、Design System 和原型。它应能准确复述用户、核心流程、范围、关键交互状态和完成标准，并给出大致收敛的实施计划。实现技术可以不同，但核心产品行为不能依赖作者继续口头补充。

### 4. 敏捷 MVP → 可行性门

先砍成一个端到端切片，用最低必要的安全、版本历史和行为验收确认核心流程是否可行、是否有人需要。不要在产品假设尚未验证时先做完整架构和测试体系。

### 5. 可行后再工程化与交叉 Review

确定继续投入后，再按风险补重构、测试矩阵、CI、错误处理、监控和安全；由独立模型查看 PRD、Spec、diff 和测试证据做交叉 Review。修改后必须复测。

## 自适应规则

- 已有 PRD：检查它是 v0 还是经过原型反写的 v1。
- 已有原型：直接做原型 Review、反写 PRD 和 Spec。
- 已有 MVP：先过可行性门，再决定继续工程化还是回到需求。
- 非 Web 项目：保留流程节点，替换 Lovable 为适合该作品的可见或可操作原型工具。

## 完成证据

学生能画出自己的当前阶段，指出下一节点的输入、产物和拍板责任；并能解释为什么 PRD 要用独立交接测试判断，而不是按页数判断。
