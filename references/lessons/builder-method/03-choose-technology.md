# Design System、Lovable、PRD v1 与 Spec

## 目标

先给原型明确的设计约束，再让原型暴露需求问题，最后反写 PRD 并让 AI 产出 Spec。

## 讲授

Alan 的 Web 默认流程不是“先写完整 Spec 再看页面”，也不是让 Lovable 无约束自由发挥，而是：

```text
PRD v0
→ Design System
→ Lovable 原型
→ 通过原型发现遗漏
→ 反写 PRD v1
→ AI 产出 Spec
```

Design System 至少说明产品语气、颜色角色、字体层级、间距、圆角、组件规则和关键交互状态。它给 Lovable 统一约束，但不需要第一版就写成庞大的品牌手册。

学生查看原型后逐项决定保留、删除、修改和新增。Agent 把已确认的产品决策写回 PRD v1，再结合 PRD v1、Design System 和原型生成技术 Spec。技术选型不是排行榜，要说明数据、接口、权限、部署、验收、风险、非目标和备选。

PRD v1 的质量用实现收敛度判断：不同开发者或 AI 只读同一组材料，应该理解相同的核心产品行为。PRD 不需要规定每一行代码；技术实现由 Spec 收敛，但核心流程、交互意图、范围和成功标准不能靠作者脑补。

## 实验

1. 从 PRD v0 和参考产品生成最小 `DESIGN_SYSTEM.md`。
2. 把 PRD v0 与 Design System 交给 Lovable，生成核心流程原型；无法使用时选 baoyu-design 或其它合适原型工具。
3. 学生真实查看原型，标记保留、删除、修改和新增。
4. Agent 输出 PRD v1，并列出 v0 → v1 变化。
5. 启动一个未参加前序讨论的独立 Agent，只给它 PRD v1、Design System 和原型；要求复述核心流程、非目标、关键状态、验收标准和实施计划，并列出必须澄清的问题。
6. 对仍需猜测的核心决策继续反写 PRD v1，直到通过交接测试。
7. Agent 查当前官方文档，输出 `SPEC.md`：推荐方案、技术理由、数据、接口、约束、验收、风险、暂不需要什么和一个备选。
8. 学生只裁决产品意图、不可逆选择和关键 trade-off，不被迫回答纯技术细节。

## 证据

Design System、原型、PRD v1 和 Spec 能互相对应；独立 Agent 不依赖原对话也能准确理解并提出大致收敛的实施计划；没有因为热门自动加入登录、数据库或复杂框架；原型代码未被默认当成生产工程基座。
