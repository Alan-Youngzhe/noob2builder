# 出问题先分层：请求、状态码与诊断卡

## 目标

学生遇到"报错了"时，不再把整段错误原样甩给 Agent 让它盲试，而是能先判断问题大致在哪一层，再有针对性地提问。

## 讲授

盲目试错是小白和 Agent 一起烧时间的主要方式：Agent 猜一个原因、改一处、还是不行、再猜。破解办法是**先分层，再动手**。

一次典型的 Web 请求要穿过这些层，任何一层都可能是故障点：

```text
本机环境 → 网络可达 → 域名解析 → 服务进程 → 认证授权 → 业务代码 → 数据 → 外部依赖
```

分层最快的入口是**看错误发生在哪一步就停住了**：

- 命令根本没跑起来（找不到命令、权限不足）→ 本机环境；
- 连不上、超时 → 网络或服务没起；
- 有响应但是 4xx → 请求这边的问题（地址、参数、认证、权限）；
- 有响应但是 5xx → 服务那边的问题（代码报错、依赖挂了）；
- 200 但结果不对 → 业务逻辑或数据，链路是通的。

最后一条最容易被忽略：**HTTP 200 只证明服务器正常回了一句话，不证明它做对了事**。第一次遇到状态码时读 `../shared/http-status-codes.md`。

给 Agent 提问的正确姿势不是"报错了怎么办"，而是："我判断问题在 X 层，因为 Y；这是完整错误文本；请先确认我的判断对不对，再给一个可验证的下一步。"

常见误区：把警告当错误；只截图错误的最后一行（关键信息经常在上面）；连续接受 Agent 的猜测而不要求它先定位。

## 实验

1. 启动一个本地服务，用 `curl -i` 制造并记录三种真实结果：一次成功（2xx）、一次 4xx（访问一个不存在的路径）、一次 5xx 或连接失败（停掉服务再请求）；
2. 每一次都完整读响应：状态码、响应头、响应体分别说明了什么；
3. 让学生在不看 Agent 回答的前提下，先自己判断每一次故障属于哪一层；
4. 再让 Agent 独立判断一遍，对比两个结论，不一致时追问依据；
5. 生成 `MY_DIAGNOSIS_CARD.md`：左边是现象，右边是"先查哪一层、用什么命令查"。

无法真实制造 5xx 时用"停掉服务后请求"替代，并在存档中注明这是连接失败而非服务端错误。

## 常见误区

- 同一个现象可能有多层原因，分层是缩小范围，不是一次锁定；
- Agent 连续两次修不好同一个问题时，停下来重新分层，而不是让它继续试第三次；
- 诊断卡是给自己用的，写自己看得懂的话，不要抄通用清单。

## 证据

学生提交 `MY_DIAGNOSIS_CARD.md`，并能演示一次完整的"先判断层 → 选命令 → 验证 → 确认或推翻判断"。三次 `curl -i` 的真实输出入档；演练的部分标记为 `simulated`。
