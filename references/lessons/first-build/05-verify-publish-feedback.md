# 可行性之后：工程质量、交叉 Review 与发布

## 目标

只有 MVP 核心方案通过可行性门后，再投入与产品风险相称的工程质量、测试和跨模型 Review，最后完成正式发布。

## 讲授

敏捷 MVP 不是永远停在“能跑”。可行性成立后，Agent 先体检当前实现：重复和脆弱结构、关键错误路径、数据与权限风险、测试缺口、部署和监控需求。再按风险补质量，而不是追求 100% 覆盖率。

开发 Agent 完成改进后，用另一个模型或独立 Agent 做交叉 Review。Review 必须查看真实 diff、PRD v1、Spec、测试结果和风险；同一 Agent 的自查不能冒充独立交叉 Review。逐条记录采纳、拒绝和原因，修改后重跑验证。

发布方式由作品决定：网页可以部署，脚本可以打包并给运行说明，Skill 可以通过仓库或安装包分发，数据工具可以交付模板和样例。部署不是唯一发布方式。

## 实验

1. 确认可行性门已经通过；没有通过就回到需求或 MVP，不做工程化表演。
2. 生成风险与测试矩阵，补关键行为、历史 Bug 和高风险路径。
3. 运行项目适用的真实测试和构建，保存退出结果。
4. 让独立模型做交叉 Review，逐条处置并复测。
5. 故意制造一个失败，确认界面或日志能暴露并恢复。
6. 选择交付方式并正式发布。
7. 从另一设备、无痕窗口或第二个用户入口验证。
8. 收集真实反馈，修复一项问题或明确拒绝一项无关需求。
9. 读取 `../shared/evidence-card.md` 生成证据卡。

## 证据

可行性记录、交付地址或使用说明、真实测试、交叉 Review 处置表、失败修复、用户反馈和证据卡。外部服务不可用时只能标记 blocked，不能把本地页面写成已上线。
