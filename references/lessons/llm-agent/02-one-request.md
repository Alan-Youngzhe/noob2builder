# 一次请求里到底发生了什么

## 目标

学生能画出一次对话请求的完整构成，理解"模型不记得上一轮"这个事实，以及为什么每次都要重发全部历史。

## 讲授

你在对话框里敲一句话，实际发出去的远不止这一句。API 层面，一次请求是一个**消息数组**，每条消息带一个角色：

```text
system     ：身份、规则、可用工具的说明
user       ：你之前说过的每一句
assistant  ：它之前回过的每一句
user       ：你这一句（新的）
```

模型收到这一整包，生成回复，**然后就结束了**。它不保留任何东西。下一轮之所以能接上，是因为客户端把上面所有内容又原样发了一遍，只是末尾多了一条。

这解释了三件小白常困惑的事：

- **为什么聊久了变贵**——每一轮的输入都在变长，而输入按 token 计费。第 20 轮那次请求，把前 19 轮全带上了；
- **为什么聊久了它开始忘前面**——历史超出 Context Window 后必须被裁掉或压缩。主流模型的上限目前在 20 万 token 这个量级，具体数字以现场查证为准；
- **为什么开新对话它就不认识你了**——它本来就从不认识，是历史消息在扮演记忆。

**system 层**优先级更高、更稳定，用来放身份和规则；**user 层**放这次的具体任务。规则写进 system 层比每轮重复更省也更可靠——Claude Code 的 `CLAUDE.md`、Skill 的说明文件、`~/.claude/settings.json` 里的配置，本质都是在往这一层写东西。你现在上的这门课能生效，就是因为 `SKILL.md` 被放进了这一层。

常见误区：以为模型有个人档案；以为"你上次说过"是它记得；以为在界面上删掉一条消息，模型就没看见（要看客户端是否真的从请求数组里去掉了）。

## 实验

1. 在一次对话中告诉 Agent 一个只有你知道的事实，然后**新开一个会话**再问它，观察结果；
2. 回到原会话再问一次，让 Agent 解释这两次的差别来自哪里；
3. 打开 `~/.claude/CLAUDE.md`（如果有）看一眼，确认那里面的内容确实在每次会话都生效——这是 system 层的实物；
4. 让 Agent 估算当前这次请求里，system、历史、附带资料各占多少 token，说出哪一块最大；
5. 读入一个大文件让对话显著变长，再观察响应变化；
6. 输出 `MY_REQUEST_FLOW.md` 第一版：把上面那个消息数组，换成自己这次真实请求的内容。

## 常见误区

- "记忆功能"是客户端在请求里塞进了摘要或检索结果，不是模型自己记住了；
- 附带资料越多不等于越准，无关资料会稀释注意力；
- 同一句提示词在不同 system 内容下表现不同，评价提示词必须说清环境。

## 证据

`MY_REQUEST_FLOW.md` 第一版，包含学生这次请求的四个角色分层，以及第 1、2 步的真实对比结果。
