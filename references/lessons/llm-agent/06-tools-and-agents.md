# 从"会说"到"会做"：工具调用、ReAct 与 MCP

## 目标

学生能指出一次真实工具调用的每一步分别由谁执行，分清 Function Calling、MCP、Skill、Subagent 各自解决什么问题，并完成自己的请求链路图。

## 讲授

模型本身**不能**读文件、跑命令、上网。它只能输出文本。所以"Agent 会操作电脑"这句话严格说是错的——真正动手的是宿主程序。

一次工具调用的分工是这样的：

```text
宿主程序告诉模型：你可以用这些工具，各自要什么参数
→ 模型输出一个结构化的调用请求（工具名 + 参数）      ← 模型只做到这里
→ 宿主程序真的去执行（读文件 / 跑命令 / 发请求）      ← 这一步是宿主
→ 把执行结果作为新消息放回 Context
→ 模型看到结果，决定继续调用还是给出回答
```

这个"输出结构化调用请求"的接口叫 **Function Calling**（Anthropic 的叫法是 Tool Use）。模型说"我要调用 `read_file`，参数是这个路径"，仅此而已。

**ReAct** 是这个循环的经典命名，Reasoning + Acting：思考 → 行动 → 观察 → 再思考。你在 Claude Code 里看到它"先看文件，再改，再跑测试"，走的就是这个循环。

再往上是三个经常被混为一谈的东西，其实各管一层：

| 名字 | 是什么 | 解决的问题 |
|---|---|---|
| **Tool / Function Calling** | 模型能提出的一个具体动作 | 让模型能操作外部世界 |
| **MCP**（Model Context Protocol） | 一套开放协议，让外部服务以统一方式提供工具 | 每接一个新服务不用重写一遍对接 |
| **Skill** | 一份写给 Agent 看的说明书（本质是 Markdown） | 让 Agent 在特定任务上按既定方法做事 |
| **Subagent** | 派一个独立上下文的分身去干一段活 | 隔离上下文、并行处理，避免主线被撑爆 |

一句话区分：**MCP 给的是"能力"，Skill 给的是"做法"。**你现在上的这门课就是一个 Skill——它没有给 Agent 任何新工具，只是规定了它该怎么教你。

顺带看一眼这几年是怎么走过来的：2022 年底能力还基本停在"会说"，靠人复制粘贴；2023 年 Function Calling 让模型能提出结构化动作；2024 年前后 MCP 这类协议开始统一工具接入；再往后重心明显从"模型更聪明"转向"环境更可靠"——规则文件、权限、验证命令、可恢复的循环。**能力提升的很大一部分不来自模型本身，而来自它周围的工程。**这条线索在 ⑥《从 Prompt 到 Graph》里展开。

常见误区：以为 MCP 装得越多越强（工具描述本身占 Context，还会互相干扰）；以为 Skill 是插件程序（它就是文本）；以为 Subagent 越多越好（隔离的代价是它看不到主线的上下文）。

## 实验

1. 给当前 Agent 一个必须动手的任务：在临时目录建两个文本文件、比较内容、生成摘要文件并读回；
2. 全程让它**逐步暴露**：这一步是模型的判断，还是宿主的执行？工具名和参数是什么？返回了什么？
3. 用 `/mcp` 或等价方式列出当前接入的 MCP 服务，说出每个提供了什么能力；
4. 打开 `~/.claude/skills/` 看一个真实的 Skill 文件，确认它只是 Markdown；
5. 完成 `MY_REQUEST_FLOW.md` 终版：从你敲下一句话开始，到 system 层、历史、资料、工具调用、执行、结果回灌，画完整一条链路；
6. 让一个没参与过这次对话的 Agent 只读这份链路图，复述一遍。它说错的地方就是图没画清的地方。

## 常见误区

- 纯聊天演示不算工具实验，必须有真实的文件或命令产物；
- 工具执行失败时模型看到的是错误文本，它可能因此重试或换路——这不是它"知错了"，是新信息进了 Context；
- 权限是宿主控制的，模型请求删除不等于会被执行。

## 证据

`MY_REQUEST_FLOW.md` 终版，包含真实的工具调用记录、生成的文件和第 6 步的交接测试结果。学生能说出 Tool、MCP、Skill、Subagent 各自解决什么问题，不用比喻也能说清。
