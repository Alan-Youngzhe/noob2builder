# 共享节点：HTTP 状态码与联调排错

## 什么时候加载

第一次做 Web/API 请求、前后端联调、部署后排错，或遇到 `401`、`404`、`429`、`500` 等状态码时加载。它不是让学生背完整标准，而是先判断问题大致发生在哪一层。

## 一句话理解

HTTP 状态码是服务器对一次请求返回的三位数答复。先看首位数字，再看具体状态码、响应头、响应体、浏览器 Network 面板和服务端日志。

| 首位 | 类别 | 先问什么 |
|---|---|---|
| `1xx` | 信息 | 请求还在协商或处理中吗？ |
| `2xx` | 成功 | 服务器是否完成了期望动作？ |
| `3xx` | 重定向 | 客户端是否需要去另一个地址，或使用缓存？ |
| `4xx` | 请求无法按当前请求完成 | URL、参数、身份、权限或频率哪里不对？ |
| `5xx` | 服务器未能完成请求 | 服务端、上游依赖、网关或超时哪里失败？ |

这是一种排错路由，不是简单的“谁背锅”：某些 5xx 可能由上游输入、配置或依赖触发，仍要看证据。

## 常见状态码

### `2xx`：成功

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| `200 OK` | 请求成功并通常有响应体 | 页面、查询 API、普通更新 |
| `201 Created` | 新资源创建成功 | POST 新建报名、用户或文件 |
| `204 No Content` | 成功但不返回响应体 | 删除或更新成功后无需返回数据 |

`201` 和 `204` 不是 POST/PUT 的硬性绑定；真正语义由 API 合同决定。

### `3xx`：去别处找

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| `301 Moved Permanently` | 永久重定向 | 域名或路径永久搬家 |
| `302 Found` | 临时重定向 | 短链接、应用把未登录用户送去登录页 |
| `304 Not Modified` | 资源未变化 | 客户端按缓存使用已有内容 |

遇到 3xx 时查看 `Location`、缓存请求头和浏览器最终落到的地址；不要只把“页面没打开”归因于后端挂了。

### `4xx`：当前请求需要修正

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| `400 Bad Request` | 请求格式或参数不正确 | JSON 语法错、缺少字段 |
| `401 Unauthorized` | 未通过身份认证 | 没带 token、token 过期或无效 |
| `403 Forbidden` | 已识别身份但不允许访问 | 普通用户访问管理员资源 |
| `404 Not Found` | 路径或资源不存在 | URL 写错、资源被删、路由没注册 |
| `409 Conflict` | 与当前资源状态冲突 | 重复报名、版本冲突 |
| `422 Unprocessable Content` | 格式能读但业务校验不通过 | 邮箱格式、字段组合不满足规则 |
| `429 Too Many Requests` | 请求频率或配额超限 | 触发限流、API 超配额 |

记忆：`401 = 你是谁？`；`403 = 我知道你是谁，但你不能进。`

### `5xx`：服务器链路没有完成

| 状态码 | 含义 | 常见场景 |
|---|---|---|
| `500 Internal Server Error` | 服务端未处理的异常 | 后端代码抛错、错误没有兜底 |
| `502 Bad Gateway` | 网关从上游得到无效响应 | 反向代理后的应用挂了或返回异常 |
| `503 Service Unavailable` | 服务暂时无法处理 | 过载、维护、依赖暂不可用 |
| `504 Gateway Timeout` | 网关等待上游超时 | 后端或数据库处理过慢 |

实用口诀：

- `2xx`：动作大概率完成，仍要验证数据和业务结果；
- `3xx`：查看跳转和缓存；
- `4xx`：检查 URL、参数、身份、权限、冲突和频率；
- `5xx`：沿服务端、网关、上游依赖和日志继续追踪。

## 先看状态码，再看响应体

不要只看页面上的“失败”或 Agent 的“接口正常”。至少记录：请求方法、URL、状态码、关键请求头、响应体摘要、浏览器最终地址、服务端日志和重现步骤。`HTTP 200` 也可能包着 `{ "success": false }`，状态码通过不等于产品动作完成。

## 实验

1. 用当前项目或一个临时本地服务，执行 `curl -i <URL>`，观察状态行、响应头和响应体。
2. 主动制造四类结果：成功请求、错误参数、未认证请求、不存在的路径。
3. 如果项目有登录或限流，再观察 `403`、`429` 或对应降级行为；没有就用纸面演练并标记 `simulated`。
4. 写一张 `HTTP_DEBUG_CARD.md`：请求、状态码、初步归因、下一步证据和最终修复。
5. 用浏览器 Network 面板或命令行再次验证修复，不接受“代码看起来对”作为完成证据。

## 彩蛋（不作为必背内容）

`418 I'm a teapot` 来自 RFC 2324 的愚人节文本，很多框架会把它当作彩蛋；公司自定义状态码也不能替代清晰的 API 合同。遇到非标准码时先看服务方文档，不要按通用语义猜测。
