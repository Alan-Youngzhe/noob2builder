# 测试层级与测试矩阵

## 目标

知道单元、集成、冒烟和 E2E 各自保护什么，并能为当前项目分配测试层级，而不是把所有东西都写成浏览器测试。

## 四种测试

| 类型 | 保护对象 | 速度与定位 | 活动报名例子 |
|---|---|---|---|
| 单元测试 | 一个函数或模块 | 最快、最容易定位 | 手机号校验、重复报名判断 |
| 集成测试 | 多个真实模块的边界 | 中等、能发现连接错误 | API + 测试数据库写入 |
| 冒烟测试 | 少量最关键的系统路径 | 快速、广而浅 | 首页、健康检查、最小提交 |
| E2E 测试 | 完整用户旅程 | 最慢、最接近用户 | 打开页面、填写、提交、后台查看 |

冒烟测试是“测试范围和目的”，不特指某个技术层。它可以是 API 脚本，也可以是浏览器动作。E2E 可以实现验收场景，但不是所有验收都必须用 E2E。

## 实验：生成测试矩阵

为每个风险填写：

| 行为 / 风险 | 正常 | 边界 | 失败 / 安全 | 最低证据层 |
|---|---|---|---|---|
| 创建报名 | 合法字段 | 超长姓名 | 重复提交 | 集成 + 冒烟 |
| 查看名单 | 有记录 | 空名单 | 普通用户越权 | 集成 + E2E |

先用最便宜的层覆盖；低层无法证明真实边界时再升到集成或 E2E。

## 共识

- 测试应独立、可重复、尽量快速；
- 关键行为优先于追求 100% 覆盖率；
- 每个历史 Bug 都应留下回归测试；
- 钱、权限、删除、隐私和外部副作用需要测试之外的人工 Review。

## 证据

提交当前项目的 `TEST_MATRIX.md`，并解释至少一个“为什么不用 E2E 测”的例子。
