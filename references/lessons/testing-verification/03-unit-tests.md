# 单元测试：保护纯逻辑

## 目标

让一个函数在隔离环境中，对明确输入稳定地产生正确输出。

## 怎么写

先找输入输出清楚、没有网络和数据库副作用的逻辑：

```text
输入：手机号为空
预期：返回“手机号必填”

输入：手机号格式错误
预期：返回“手机号格式不正确”

输入：合法手机号
预期：校验通过
```

测试保持 Arrange → Act → Assert：准备数据，调用行为，断言结果。一个测试只回答一个主要问题，测试名描述行为而不是实现方法名。

## 让 Agent 实操

1. 让 Agent 先查项目已有测试 runner，不要自动安装第二套框架。
2. 让它找一个纯函数并解释为什么适合单元测试。
3. 先写一个会失败的边界测试，再修复实现。
4. 运行项目真实命令，保存退出码和输出。

## 常见误区

- 只测 happy path；
- 断言内部函数被调用几次，却不检查最终行为；
- 为了让测试绿而放宽真实业务规则；
- 把所有依赖都 Mock，导致测试没有现实价值。

## 证据

至少一组正常、边界和失败单元测试；包含一次 RED → GREEN 记录；说明没有覆盖的外部边界。
